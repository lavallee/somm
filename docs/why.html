Why build this

The usual advice is to put a gateway in front of your providers and send traces to an observability product. For many people that is the right answer, and this page says when. somm exists for a narrower case: one developer, a dozen projects, no operations budget, and a wish for each project to start from what the others learned.

The argument

  1. The unit of learning is your whole machine, not one project. A model decision made in one project is stored machine-wide by design and found from any other. A tool that keeps one project's traces cannot do this however good it is. In November 2026 no tool surveyed combined cross-project decision memory, grading of production traffic that feeds routing, a local ledger and a surface a coding agent can ask (VISION.md, "Re-grounding, November 2026").
  2. Cost is not always dollars. Coding plans and subscription seats run out by the window. Gateway budgets are typically dollar limits per key over a period; LiteLLM's proxy, for example, sets max_budget with a budget_duration and keeps keys and spend in Postgres (LiteLLM docs, checked 2026-11-09). somm records quota windows, paces against them and learns limits from your own rate-limit errors. The failure it guards against is real: a week in July 2026 in which 91.1% of 306,734 calls failed while marginal spend was near zero (incident).
  3. The record has to be the truth. Grading, comparing and recommending are only as good as the rows under them. somm owns the provider layer so that a pin never substitutes a model, every failure is recorded against the model asked for, and a telemetry failure never breaks or repeats a paid call (CHANGELOG.md, 0.20.2). Wrapping someone else's client would put those guarantees in code it does not control.
  4. Not every workload should stay a model call. A router chooses between models. A handler lets a rule take over part of a workload under the same name, so "should this still be a model call?" becomes a query (the climb; gabe's same_event, 700,000 calls on a 7B local model, VISION.md).
  5. Coding-agent attempts are calls too. They are often the most expensive thing a project does, and the harness that ran a model changes the result too (VISION.md, "Strategy bets"). somm records each attempt in the same ledger as API calls (harnesses).
  6. Your data and your tools should outlast vendors. One SQLite file per project, no account, no phone-home, works offline with Ollama. The field moves quickly; facts checked on 2026-11-09 from each project's own pages:
    • Langfuse joined ClickHouse in January 2026; both say the MIT core and self-hosting are unchanged (Langfuse).
    • Traceloop, maker of OpenLLMetry, joined ServiceNow in March 2026 (Traceloop).
    • promptfoo joined OpenAI on 9 March 2026 and says it stays MIT (promptfoo).
    • TensorZero's repository was archived on 12 June 2026 (GitHub).
    • OpenAI Evals became read-only on 31 October 2026 and shuts down on 30 November 2026 (OpenAI deprecations).
    • Malicious LiteLLM releases 1.82.7 and 1.82.8 were published to PyPI in March 2026 (LiteLLM issue #24518); VISION.md counts two compromised releases of the library in 2026.
    None of this says those tools are bad. It says a single developer cannot re-platform every year, and that a file you own does not get acquired.

Objections, and honest answers

"Just use a gateway plus a tracing product."
If you have one or two projects, a team, or a need for a trace viewer, annotation queues and single sign-on, do that. What the pair does not give you is listed above: decisions remembered across projects, subscription windows as a routing input, agent attempts on the same ledger, rule-served work under the same name. It is also two services to run. somm can sit beside one: it has an OpenTelemetry exporter plugin (somm[otel]), though aligning it with the current conventions is still ROADMAP phase 4.
"You depend on LiteLLM anyway."
Not as code, since 0.24.0. Until then somm-service depended on litellm and its proxy routes called it directly; the proxy now runs on somm's own client and nothing in somm imports LiteLLM (CHANGELOG.md, 0.24.0). One use remains, as data: the bundled price snapshot is generated from LiteLLM's published price file, fetched as JSON by a maintainer script (scripts/update_pricing_bundle.py). The library's only third-party dependency is httpx.
"SQLite won't scale."
It does not need to scale far: one file per project, one developer. The October census read a shared ledger holding 1.7 million calls since June (CHANGELOG.md, 0.17.0). There are no published load tests. The somm[postgres] extra installs only a driver, for shared-deployment experiments (README.md).
"OpenRouter already routes and shows costs."
It is a hosted service; somm runs on your machine and uses OpenRouter as one provider among eleven. OpenRouter's own routing options include a zero-retention filter (OpenRouter docs, checked 2026-11-09), and somm uses OpenRouter's published list to decide when a model meets a zdr boundary (0.22.0). If one bill for many models is all you need, use OpenRouter alone.
"Is the memory real?"
Not proven yet. Recalls are not stored, and in November nearly every decision in the shared ledger had been written by a test fixture (VISION.md). The design is in place; the evidence is not.
"The recommendations were wrong."
Many were. In October, 40 of 49 open recommendations came from one rule misreading one column, fixed in 0.17.2; by November 54 had been created and none applied (CHANGELOG.md, VISION.md). Finding that out is what the ledger is for.
"It is pre-1.0."
Yes, and the release gate refuses a 1.x version without a written decision that the API is ready (RELEASING.md).
"It is one person's project."
It is built by one developer for that developer's projects first. The mitigation is that it is MIT-licensed, the data is plain SQLite, and BLUEPRINT.md writes the design down for anyone who wants to rebuild it.
"I don't write Python."
The library is Python 3.12 or later. Other programs can use the proxy routes or send OpenTelemetry traces to the service, with the proxy's current limits described here.

When to use something else

  • A team that needs a shared hosted dashboard, single sign-on or annotation queues: use a tracing platform. somm is built for one person.
  • A production gateway for many services at high request rates: use a dedicated gateway. somm's proxy has no published load numbers.
  • One project, one provider, no grading: the provider's own SDK is enough.
  • Only a searchable log of prompts in SQLite: Simon Willison's llm keeps one (simonwillison.net).
  • A trace viewer for local use: Arize Phoenix runs locally under the Elastic License 2.0 (GitHub); somm's traces can be exported to a viewer like it.

What somm still depends on, and has not proven

  • Depends on: LiteLLM's published price file, as data, for the price snapshot; models.dev and OpenRouter's catalogue for model intel; the providers' own terms for every tier above local.
  • Not proven: that decisions are recalled across projects (unmeasured); that a recommendation gets applied because of its evidence (none yet); that coding agents use the MCP server and skill (installed in none at the November audit); that most of a climb is visible to the ledger (it is not yet).
  • Not published: load numbers, dashboard screenshots, a recorded demo.

ROADMAP.md's November sequence puts a trustworthy record first and this explanation last, for that reason.
