The meter and the memory for your model calls.

somm is a Python library that records every call your projects make to a language model in a SQLite file on your own machine, and remembers which model you chose for which job, so the next project starts from what the last one learned.

Self-hosted and MIT-licensed. No account, no hosted service, nothing sent to the somm project. It works offline with only Ollama running. Built for one developer with many projects. 

$ pip install somm
$ python -c "
import somm
llm = somm.llm(project='my_app')
r = llm.generate('Reply: pong', workload='ping')
print(r.text, r.provider, r.call_id)
"
$ somm status --project my_app   # the row that call just wrote

The idea

The meter

Every call writes one row to the ledger, a SQLite file in your project: which workload asked, which provider and model answered, the tokens, the latency, the cost and how that cost was worked out, the outcome, and how far the data travelled. Failures get a row too. You can read it with plain SQL.

The memory

Rows alone are a log. somm turns them into memory three ways: a sample of real calls is graded against a stronger model (shadow evaluation); rules turn the grades into recommendations you apply or dismiss; and each model choice you make is kept, with its reason, in a machine-wide store that every project and your coding agent can search.

Pick once, remember everywhere

The demonstration of the memory. Your coding agent talks to somm through its MCP server. In one project you ask which model to use and record why you chose it; weeks later, in another project, the agent finds that decision before it suggests anything.

Illustration, not a recorded session 
# project A, week 1, in your coding agent
you   > which local model for pulling dates out of emails?
agent → somm_advise(question=...)          # ranks candidates: model intel + your history
you   > qwen3:14b. gemma kept missing dates in long threads.
agent → somm_record_decision(...)          # stored with the reason, machine-wide

# project B, week 3
agent → somm_search_decisions(question="date extraction")
        # 1 prior decision: qwen3:14b, from project A, with the reason

The three tools are real (packages/somm-mcp); the conversation above is an example of their use. How often this actually happens is the number somm is judged by, and it is not measured yet.

The loop

Five steps, each reading and writing the same ledger. Select a step to read about the part of somm that does it.

  • Record. The client writes one row per call, including failures.
  • Grade. For workloads you opt in, a background worker re-runs a sample on a gold model and scores the match.
  • Recommend. Rules read grades, costs and failures and write proposals, each with its evidence, to the inbox.
  • Apply. You, or your coding agent, apply or dismiss each one. The only change somm makes by itself is raising a max_tokens floor, and only for a workload that opts in.
  • Remember. An applied change, or a choice made in conversation, is stored as a decision every project can recall.

The components

One sentence each. The components page tells the problem each one solves, how it connects, and the evidence for it.

Client, providers and streaming
somm.llm() returns one client that talks to eleven built-in providers (eight APIs and three subscription seats) and any OpenAI-compatible server, with JSON, typed errors and streams on the same call path.
Routing, cooldowns and pins
Tries providers in order, rests a failing model for a while, and serves a call that names its model with exactly that model or fails.
Ledger, mirror and the ledgers on a machine
One SQLite file per project, plus a machine-wide copy so one query can span every project, and commands that show every ledger and fill the mirror's gaps.
Workloads
A named job your code asks for, such as claim_extract; cost, failures, rules and recommendations all attach to it.
Data boundary
How far a workload's data may travel, on a four-step scale, enforced before any request leaves the process.
Shadow evaluation and judges
Grades a sample of real calls against a stronger model, so you learn whether a cheaper one is good enough.
Recommendations and the inbox
Rule-made proposals with their evidence, waiting for you to apply or dismiss.
The sommelier
Decision memory: ranks candidate models and remembers which you chose, and why, across projects.
MCP server and skill
Fourteen tools a coding agent can call, plus instructions that teach it to use somm instead of writing its own wrapper; one command installs each.
Service and dashboard
A local web app (somm serve) with a dashboard, a JSON API and the scheduler for the loop.
The proxy
Anthropic- and OpenAI-shaped HTTP routes, run on somm's own client, so a program you cannot edit can send its calls through somm.
Plans and quota pacing
Knows that a subscription runs out by the window, not by the dollar, and slows down before it does.
Harnesses
Runs one Claude Code, Codex, OpenCode or Pi attempt and records it in the same ledger as API calls.
Decision calls
Asks a decision model a typed question and gets a label and a probability back, recorded like any call.
Workload handlers and the climb
Lets a rule or other component serve part of a workload instead of a model, measured under the same name; somm climb reports each rung.
Rented GPUs
A read-only report of rented-GPU spend, and a model on a rented machine reached as a named provider.
Read API
Supported read-only functions over the ledger, so other tools stop writing their own SQL.
The CLI
The somm command: status, health, plans, inbox, loop, boundary and more.

Install

# the library: enough to record and route
$ pip install somm

# + the local web service and the MCP server
$ pip install somm somm-service somm-mcp

Python 3.12 or later. With no API keys set, somm uses a local Ollama. Each commercial provider is turned on by its own environment variable (ANTHROPIC_API_KEY, OPENAI_API_KEY, OPENROUTER_API_KEY, GEMINI_API_KEY, MINIMAX_API_KEY, DEEPSEEK_API_KEY, PERPLEXITY_API_KEY).

Already have an LLM wrapper?

# before
from myproject.llm import FooLLM
# after: call sites stay the same
from somm.compat import GenericLLMCompat as FooLLM

Run the loop and the dashboard

$ somm loop install --project my_app   # a systemd user timer; no resident process
$ somm serve --project my_app          # dashboard on http://localhost:7878
$ somm doctor --global                 # health of every project on this machine

The README is the reference: every CLI command, environment variable and provider capability. BLUEPRINT.md is the design document.

Status

v0.26.2 beta / pre-1.0 — see the CHANGELOG for the release log; 1,660 tests pass with four live Ollama checks skipped when no local server is available. The test suite runs in CI on every push. The public API, MCP tools, service contracts and migration semantics are not yet declared stable. MIT licensed.

Works today

  • Recording every call, failures included, in a local SQLite ledger with a machine-wide mirror.
  • Routing with persisted cooldowns and exact pins across eleven built-in providers, with streaming, tool calling, embeddings, structured output, typed errors and async calls.
  • The data boundary, checked on every path that leaves the process (0.21.0).
  • Plan pacing for subscriptions and metered quotas.
  • The loop as a command or a timer: model intel, shadow grading, recommendations.
  • Coding-agent attempts recorded beside API calls; a supported read API; somm ledgers, somm fleet status and somm mirror sync across a machine's ledgers.

Not yet proven

  • The memory. The north-star number, decisions recalled across projects, has no history yet: recalls have been stored only since 0.23.0, and nearly every decision in the shared ledger was written by a test fixture (VISION.md, November 2026).
  • The loop closing. Fifty-four recommendations had been created and none applied (same source).
  • Agent use. At that audit the MCP server and the skill were installed in no coding-agent harness; somm mcp install and somm skill install exist since 0.23.0, with no record of use yet.
  • Decision calls are built from the vendor's documentation and tested against fakes, not yet against the live API (docs/decisions.md).
  • Sustained use. Most of what shipped since 0.20 has not yet been run for weeks on a real fleet; no graduation test in ROADMAP.md is met.
  • The proxy runs on somm's own client (0.24.0) and streams tokens as they arrive (0.25.0), but has no published load numbers and no record of sustained use yet (CHANGELOG.md).
  • No published load numbers and no dashboard screenshots yet.

ROADMAP.md orders the work that closes these gaps, starting with a record you can trust. Why build this makes the case and says when you should use something else.
